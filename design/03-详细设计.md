# superdev 详细设计

这份文档写给实现者：每个部件的规则、脚本、表结构、状态迁移逐项给到能动手的程度。术语以 README 术语表为准。

## 1. 红绿纪律（工人契约核心）

工人的每一步被四条规则约束：从绿点开工、开工前按预算研究、改坏整体退回、两败先研究再换方向。

### 1.1 契约细则（写入 `superdev-work.md`，工人会话开场加载）

1. **基线规则**：每回合从任务所属模块的绿点开新分支 `superdev/<task-id>`。
2. **绿的定义**：该模块全量回归测试加 lint 通过，由纪律脚本判定。工人不得自报"我已经测过了"。
3. **红即回滚**：回归不过，纪律脚本执行 `git reset --hard <绿点>`，失败日志（截到 200 行）作为下一轮唯一的新增上下文喂回工人。
4. **两败转研究**：同一任务连续两次红，下一轮必须先过研究关（见 1.4），并在开头输出 `策略变更：<一句话新方向>`。新方向必须引用研究发现；纯猜测被程序拒绝，直接触发"卡住"事件。（出处：troykelly 的 research-after-failure，连败两次就停止试错去查资料。）
5. **回归隔离**：第二次红仍指向同一失败用例时，管理端把这个用例拆成独立微任务 `repro:<case-id>`，必须附一条命令就能重跑的复现脚本；原任务标记"被它挡住"。
6. **证据回传**：绿之后提交、推送、开合并请求，回传三样：链接、回归原始输出、本回合 diff 统计。

### 1.2 纪律脚本（各引擎共用，伪代码）

```python
# red_green_loop.py <task-id> —— 引擎实现回合的外层包裹
def round(task):
    base = projection.last_green(task.module)
    git(f"checkout -B superdev/{task.id} {base}")

    for attempt in 1..2:
        run_engine_round(task)              # 引擎（ZCode/Codex/…）做实现
        result = run_regression(task.module)
        log_result(result)                   # 写投影：regression_events
        if result.green:
            projection.set_last_green(task.module, result.commit)
            return emit("task_evidence", task)
        if attempt == 1:
            git(f"reset --hard {base}")      # 整体退回，日志回喂
            feed_back(result.log_tail(200))
        else:
            run_research(task)               # 事后研究（§1.4），预算按台账分档
            if not strategy_cites_research(task):
                return emit("task_stuck", task, reason="策略变更未引用研究")
            emit("task_retry_with_strategy", task)

    emit("task_stuck", task, reason="两败")
```

### 1.3 绿点怎么维护

模块接入时，跑一次全量回归，通过的提交就是初始绿点。此后两处更新：门禁合进 main 时、纪律脚本判绿时。绿点记在台账 `agents/<项目>/status.yml`（事实源），投影里存缓存。

### 1.4 研究纪律（事前 + 事后）

**事前研究：每个任务开工前做，预算由派发器按台账的任务规模字段定死，不靠 AI 自己分档。**

| 任务规模（台账字段） | 研究预算 | 研究什么 |
|---|---|---|
| trivial（改错字、改配置） | 跳过 | 直接进实现 |
| small（单文件微任务） | 最多 2 次工具调用 | 读目标文件，搜相似实现 |
| medium（功能级） | 5–10 次工具调用 | 相似实现、既有写法、可复用工具、测试怎么写 |
| large（系统级） | 单独批准 | 完整侦察加概念验证；出现即报警——管理端理应拆小 |

研究结论不超过 30 行，写进台账 `research_notes`，随任务派发注入工人开场上下文。红了之后的新发现追加进去，升级报告直接引用。查外部资料（API 文档等）默认关——私有网络按需开。

**事后研究：第二次红触发，不再允许直接重试。** 预算按上表 small/medium 档。研究焦点三样：失败用例、上一轮 diff、此前已试方向（从投影的回归事件里拼）。研究和换策略是同一个动作：`策略变更` 字段必须引用 `research_notes`，否则派发器拒绝。

## 2. Hook 清单（管理端会话装配）

配置放在 `agents/<项目>/hooks.json`，随管理端 clone 生效，不动客户端全局配置。

| 时机 | 匹配 | 动作 | 不过怎么办 |
|---|---|---|---|
| AI 写文件前 | 目标路径不在本项目台账目录 | 拦截，提示"管理端只写台账" | 拦下 |
| AI 执行命令前 | 命令含 `git commit` 或 `git push` | 拦截，提示"管理端不代做交付" | 拦下 |
| 台账写完后 | 命中 `*.yml` | 跑 `superdev.py check <文件>` | 错误信息注回会话 |
| 会话结束前 | — | 全量检查加投影一致性核对 | 列出未闭环项，阻止收尾 |

`superdev.py check` 校验八项：任务数量、分组、依赖无环、并行就绪数、引擎与工人归属、职责边界、策略变更是否引用了 research_notes、复现脚本是否存在且可执行、研究预算是否在分档表内。

## 3. 状态机

### 3.1 任务状态图

```
draft → ready → assigned → in_progress → evidence_wait → gating
                                  │             │
                                  ↓(两败)        ↓(证据不合格)
                               stuck ──→ repro_split → ready
                                  │
                                  ↓(管理端判断超出能力)
                              escalated →(专家拍板)→ ready(带新策略)
gating →(全绿+证据齐)→ merged → done
任何状态 →(人暂停)→ paused →(恢复)→ 回原状态
```

### 3.2 迁移触发表（程序持有，AI 只能提案）

| 事件 | 迁移 | 触发动作 |
|---|---|---|
| task_created | draft→ready | 检查通过后刷新投影 |
| worker_idle | ready→assigned | 派发器匹配引擎，开分支 |
| round_green | in_progress→evidence_wait | 收证据，通知门禁 |
| round_red_1 | 不迁移 | 回滚，日志回喂 |
| round_red_2 | in_progress→stuck | 触发事后研究；策略未引用研究则升级 |
| repro_split | stuck→ready（新微任务） | 生成复现脚本契约 |
| expert_decided | escalated→ready | 新策略写回台账，派发 |
| all_green | gating→merged | 合 main，台账同步回模块仓，更新绿点 |
| metrics_stall（30 分钟） | 项目级计数 | 两次 → 暂停该项目派发并升级 |

### 3.3 守护程序职责重定义（从轮询干活的变成对账的）

| 守护 | bigdev 里干什么 | superdev 里干什么 |
|---|---|---|
| 巡检 | 2 分钟轮询派工 | 兜底：漏派补派，引擎会话健康 |
| 收发 | 10 分钟收证据、合并、同步 | 兜底：门禁对账，投影与台账一致性 |
| 督办 | 30 分钟比进度，5 败升级 | 指标比对保留；升级阈值 2；卡住事件即时触发 |
| 资源守护 | 60 秒资源处置 | 原样保留 |

## 4. SQLite 投影表结构

```sql
CREATE TABLE tasks (            -- 台账 派工计划.yml 的副本
  task_id TEXT PRIMARY KEY, project TEXT, module TEXT,
  status TEXT, engine TEXT, worker TEXT,
  red_count INTEGER DEFAULT 0, strategy_changes INTEGER DEFAULT 0,
  depends_on TEXT, mr_url TEXT, updated_at TEXT
);
CREATE TABLE regression_events (-- 纪律脚本写入
  task_id TEXT, attempt INTEGER, green INTEGER,
  commit_sha TEXT, log_tail TEXT, created_at TEXT
);
CREATE TABLE decisions (        -- 决策表副本
  decision_id TEXT PRIMARY KEY, project TEXT, question TEXT,
  context_report TEXT,          -- 程序拼的"试过哪些方向"
  status TEXT,                  -- waiting/decided/escalated
  decided_by TEXT, decided_at TEXT
);
CREATE TABLE events (           -- 事件总线（带已触发标记）
  event_id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT, payload TEXT, fired INTEGER DEFAULT 0, created_at TEXT
);
CREATE TABLE metrics (          -- 督办指标（口径继承 bigdev）
  project TEXT, ts TEXT, done_count INTEGER,
  worker_hours REAL, cost_by_model TEXT
);
```

写路径只有一条：程序改台账 → 刷新投影 → 插入事件 → 派发器消费未触发的事件。

## 5. 网页决策面

继承 bigdev 网页（127.0.0.1:6010），新增一条拍板流水线：

1. **等你拍板**（页面顶部常驻）：列出所有等待中的决策。点开是程序拼好的结构化报告——失败用例、试过的每个方向（描述、diff 统计、失败日志末尾 20 行）、已花成本。
2. **一键拍板**：选一个方向（换策略 / 拆微任务 / 换引擎 / 放弃），可加备注。决定写进数据库，程序同步写回台账，事件触发派发或恢复。全程无 AI 参与。
3. **远程访问**：加 token 或反向代理认证；默认仍只监听本机。
4. **飞书推送**：出现待拍板决策时发一条带页面锚点的消息，专家手机点开就能拍。

## 6. 督办规则（升级版）

- 指标比对保留 30 分钟一次，但事件优先：任务第二次卡住立刻升级，不等周期。
- 升级报告五要素：失败用例、复现命令、已试方向（含证据）、已耗成本（按模型和思考强度分）、建议选项。
- 恢复两条路：指标回升自动恢复（继承）；专家拍板立即恢复（事件触发）。

## 7. 从 bigdev 迁移

- 台账格式向后兼容：bigdev 项目目录原样读入，绿点在首次运行时初始化。
- 引擎适配器沿用 bigdev 的 runner 体系，外面套 `red_green_loop.py`。
- hook 配置随管理端 clone 落地，不改客户端全局配置。
- `live: false` 灰度机制原样保留，superdev 新项目和 bigdev 存量项目可在同一中台并存。

## 8. 吸收项落地（竞品强项的工程化）

这一节来自竞品对比的吸收清单（05 文档）：每项是对手验证过的强项，这里是它在 superdev 里的具体形态。

### 8.1 spec-kit 格式兼容

台账新增导入命令：`superdev.py import-spec <spec-kit 目录>`。spec-kit 的 plan/tasks 文件直接转成 `派工计划.yml`，任务粒度不合拆分规则（不在 10–50 个微任务区间）的自动打回给管理端重拆。方向：spec-kit 管写规范，superdev 管执行落地，两者可串联。

### 8.2 门禁升级为质检管线

"全绿才合 main"里的"绿"从单一回归测试升级为每模块可配置的质检管线：`gate: [lint, typecheck, test, build]`，写在模块的台账配置里。管线任何一步红，等同回归红，走同一套回滚回喂流程。出处：Bernstein 的 Janitor。

### 8.3 事件日志加防篡改链

`events` 表每条记录附上一个链式签名（本条哈希含上一条哈希）。任何人可用公开命令离线验证"从任务创建到合并"的完整决策链没被改过。出处：Bernstein 的 HMAC 链式日志。

### 8.4 CI 集成：合并请求后的自动回喂

合并请求开出后，CI 适配器（GitHub Actions / GitLab CI / Jenkins 各一个薄适配器）盯流水线结果。CI 失败：日志自动回喂工人，走一轮"退回绿点→修复→重推"；再失败进两败转研究流程。本地回归和远端 CI 用同一条失败处理路径。

### 8.5 决策面加看板视图

任务按状态列成看板（待做/在做/等证据/卡住/已合并），拖拽即提案状态迁移（仍是程序裁决）。云同步（多人协作）列路线图，首期不做。

### 8.6 管理端循环加需求澄清步

管理端拆任务前先过"需求澄清"：一次只问一个问题、附选项；澄清记录写台账，成为任务验收标准的一部分。出处：Superpowers 的 brainstorming 技能。

### 8.7 评审工人（第二双眼）

新增一种工人角色：评审工。普通工人提交合并请求后，评审工先过一遍 diff（查测试覆盖、命名、明显缺陷），产出结构化评审意见；意见回喂原工人修一轮，然后才进门禁。评审工和管理端用不同引擎跑，避免同源盲区。出处：Superpowers 的 code review 技能。

### 8.8 模块知识库（跨任务记忆）

research_notes 从单任务升级为模块级知识库：每个模块积累"什么改法灵过、什么坑踩过"，由程序从历史回归事件和已合并任务里自动提炼。新任务的研究阶段先查知识库——灵过的改法直接注入研究结论，踩过的坑直接注入警告。出处：troykelly 的 memory-integration。这是研究纪律的复利：研究一次，全项目受益。
