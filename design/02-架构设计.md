# superdev 架构设计

这套系统从上到下分四层：人拍板的网页、出主意的管理端 AI 加管规则的程序层、干活的工人 AI、验收合并的门禁。这份文档讲清每块谁管什么、数据怎么流、为什么这样切。

## 总体架构图

```
┌───────────────────────────────────────────────────────────────┐
│  人（拍板决策、专家兜底）                                        │
│    网页决策面（一键拍板→落库→触发）    飞书（只发链接通知）        │
└──────────┬────────────────────────────────────────────────────┘
           │
┌──────────▼────────────────────────────────────────────────────┐
│  管理端会话（每项目一个，AI）—— 只出主意                          │
│    拆微任务 / 依赖分析 / 验收判断 / 重派决策                      │
│    hook 拦截：只准写台账；越界写代码、代提交直接挡                 │
│    台账落盘自动跑契约检查，不过就打回                              │
└──────────┬────────────────────────────────────────────────────┘
           │ 提案（写台账 = 唯一事实源）
┌──────────▼────────────────────────────────────────────────────┐
│  裁决层（纯程序，不调模型）                                       │
│    契约校验 · 状态机 · 事件总线 · 派发器 · 督办 · 资源守护         │
│    台账文件（事实源） ⇄ SQLite 投影（查询用副本）                  │
└─────┬──────────────────────────┬──────────────────────────────┘
      │ 事件触发派工               │ 事件触发：恢复/合并/升级
┌─────▼─────────────────────────────────────────────────────────┐
│  工人层（ZCode / Codex / Kimi / Claude 四引擎同一契约）           │
│    红绿纪律：绿点开工 → 红即退回 → 日志回喂 → 两败先研究           │
│    实现 / 测试 / 提交 / 开合并请求 / 回传原始证据                  │
└─────┬─────────────────────────────────────────────────────────┘
      │ 合并请求 + 原始输出 + 回归结果
┌─────▼─────────────────────────────────────────────────────────┐
│  门禁：全绿才合进 main；台账同步回各模块仓                        │
└───────────────────────────────────────────────────────────────┘
```

## 六层模型：bigdev 留下了什么，superdev 改了什么

**理念层：不变，立场说得更狠。** bigdev 的"管理端只想、工人只做"保留。追加一条总纲：AI 提案、程序裁决——AI 出主意，程序定夺。

**组织层：不变，但管理端被看管。** 层级仍是 人 → 管理端 → 引擎 → 工人。管理端的每个工具调用都被 hook 检查。

**执行层：从定时器改为事件。** bigdev 靠 2/10/15/30 分钟轮询推进；superdev 状态一变就触发，轮询降级为兜底对账。

**门禁层：不变，但检查自动跑。** 全绿才合 main、验收看证据，都保留。契约检查从"管理端记得去跑"变成"hook 自动跑"。

**界面层：网页升级为决策面，飞书降级为通知。** 拍板在网页一键完成、落库即触发；飞书只发带链接的提醒。

**收敛层：全新。** 前身没有这层，工人在坏代码上空转。superdev 新增四件：事前研究预算、红绿纪律、两败强制研究、回归问题拆成带复现脚本的微任务。

## 核心组件

### 台账（唯一事实源）

任务、决策、状态都记录在 `agents/<项目>/` 下的文件里，git 管版本。它同时是审计记录，也能被同步进各模块仓库。数据库永远不替代它。

### SQLite 投影（查询用副本）

程序把台账整理成数据库里的四张表（任务、回归事件、决策、指标），网页和派发器只读它。写路径只有一条：程序先改台账，再刷新投影。

### 状态机 + 事件总线

任务和决策的生命周期状态由程序持有，AI 只能提案迁移。迁移一落库，程序当场触发对应动作（派发、恢复督办、合并检查），不等周期。四个守护程序保留，职责改成对账：发现投影和台账不一致就修，发现漏掉的事件就补。

### Hook（管理端约束）

| 时机 | 规则 |
|---|---|
| AI 写文件前 | 目标不在本项目台账目录 → 拦截 |
| AI 执行 git 提交/推送前 | 管理端会话内 → 拦截（管理端不代做交付） |
| 台账文件写完后 | 自动跑 `superdev.py check`，失败信息注回会话 |
| 会话结束前 | 全量检查 + 投影一致性核对 |

### 工人红绿纪律引擎

每个引擎（ZCode/Codex/Kimi/Claude）一个薄适配器，共用一份纪律脚本：跑回归、红即回滚到绿点、失败日志回喂、两次失败转研究。细则见详细设计 §1。

### 评审工人（第二双眼）

普通工人开出合并请求后，评审工人先过一遍 diff，产出结构化评审意见回喂修复，然后才进门禁。评审工和管理端用不同引擎，避免同源盲区。

### CI 适配器

合并请求开出后盯远端流水线（GitHub Actions / GitLab CI / Jenkins），失败日志走和本地回归同一条"退回绿点→回喂"路径。

### 模块知识库

每个模块积累"什么改法灵过、什么坑踩过"，程序从历史里自动提炼。新任务研究阶段先查它：灵过的直接注入结论，踩过的直接注入警告。

### 网页决策面

继承 bigdev 的网页管理端（127.0.0.1:6010），"等你拍板"升级为一键决策流：看结构化报告 → 拍板 → 落库 → 秒级触发。远程访问加认证。

## 数据流：一个任务的完整旅程

```
管理端拆出微任务 T，写进台账（检查自动通过）
  → 程序刷新投影 → 事件：任务创建
  → 派发器给 T 匹配有空位的引擎
  → 工人从 T 所在模块的绿点开新分支
  → 实现回合跑回归：
      过 → 提交、开合并请求、回传证据 → 事件：证据到位
      不过 → 整体退回绿点，失败日志喂给工人（最多两次）
      第二次也不过 → 先研究，新方向必须引用研究结论
      研究后仍无方向 → 事件：卡住 → 督办拆复现微任务或升级专家
  → 门禁：全绿且证据齐 → 合进 main → 台账同步回模块仓
  → 投影刷新 → 网页完成率更新
```

## 六个关键架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 文件还是数据库 | 文件是事实源，库只做副本 | 保住 git 版本、审计、同步进模块仓三条命脉 |
| 轮询还是事件 | 事件为主，轮询对账 | 把 2~30 分钟的节奏延迟压到秒级 |
| 规则放哪 | hook 加检查程序，不放提示词 | 靠 AI 自觉等于违规是概率事件 |
| 飞书还是网页 | 网页做决策面，飞书只推送 | 拍板要落库触发；人还在飞书里，推送必须留 |
| 自建还是拼装 | 纪律自建，引擎级可换件 | 需要的全是纪律级；编排器整体拼接会双头指挥 |
| 督办阈值 | 2 次（bigdev 是 5） | 第二次重试已无新信息；早升级加强制换方向 |

## 部署形态（继承 bigdev）

- 每个项目一个管理端会话，独立 clone，人手动开。
- 工人后台任务装一次，所有项目自动纳入，总量受 `max_parallel` 限制。
- 资源守护 60 秒一轮：单进程超 8G 结束、空闲内存低于 10% 结束最大进程、清理孤儿会话、过载时停开新会话。
